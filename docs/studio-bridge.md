# Local Studio bridge

The bridge adds explicit Studio session targeting to `rojo serve`. It is opt-in and local-only. It does not save or publish places, and it does not accept Luau source to execute. The `test` and `spec` operations do run the place's existing and synced scripts.

## Connect

Create a secret outside tracked source, in a per-user directory such as `%LOCALAPPDATA%\Rojo\studio-token` on Windows or beneath the worktree's Git metadata directory. `git rev-parse --absolute-git-dir` identifies that directory even in a Git worktree. Create the parent directory before creating the token. On Unix the file is created with mode `0600`. On Windows, `rojo studio token` removes inherited permissions with `icacls` and grants access to the current user only; it warns and keeps the file if that fails.

```text
rojo studio token --output <private-token-file>
rojo serve <project> --studio-token-file <private-token-file>
```

Connect the matching Rojo plugin to that server normally. The bridge registers only after initial sync and the sync WebSocket have connected. Then discover the exact Studio session ID:

```text
rojo studio --token-file <private-token-file> --json sessions
rojo studio --token-file <private-token-file> --json status --session <session-id>
rojo studio --token-file <private-token-file> --json capabilities --session <session-id>
```

Use `--address http://127.0.0.1:<port>` when serving on another port. The CLI refuses remote addresses and disables HTTP proxies. Every operation except listing sessions requires an explicit session ID; it never chooses an arbitrary open Studio window.

Sessions report their canonical project path, workspace path, initial Git HEAD and branch when available, and unique server/session IDs. Each listed session also reports `registeredAt` (Unix milliseconds) and `lastSeenMs` (milliseconds since its last poll), alongside the plugin-provided `placeId` and `placeName`. Session IDs are UUIDs and may be given in any standard spelling; the server stores and reports the lowercase hyphenated form.

With the bridge enabled, normal Rojo sync and bridge commands stop when the workspace switches to another checkout or the starting branch is rewritten. A new commit on the starting branch is accepted when the previously accepted commit is its ancestor (commits, merges, fast-forward pulls) or when it has the same parent (amends). Anything else, such as `git reset --hard` to another commit (including an earlier one), `git checkout -B`, `git branch -f`, a forced or rebasing pull, or amending a root commit, is rejected with HTTP 409, and sync sockets close with code 1008. Both say to restart `rojo serve`, or return to the original branch and commit, and then reconnect Studio: moving the branch back to the accepted commit resumes sync on the same server. Switching branches or detaching HEAD is also rejected. When serve starts on a detached HEAD, moving it to a descendant commit is accepted and moving it anywhere else is rejected. While a rebase, cherry-pick or revert is in progress (Git's `rebase-merge`, `rebase-apply` or `sequencer` directory exists), HEAD moves through intermediate commits, so the checkout is not judged until it finishes. Aborting returns to the accepted commit. A finished rebase is judged like any other change: rebasing onto new upstream commits rewrites the branch, so it is rejected, while a rebase that leaves the branch where it was is accepted. On each request the server reads `HEAD` from the worktree's own Git directory and the branch from the loose ref or `packed-refs` in the common Git directory, and runs Git only when the branch or a detached HEAD moves. Object names read from these files must be full hexadecimal IDs before they are passed to Git; anything else is treated as unreadable. Repositories using the reftable backend keep a placeholder in `HEAD`, so the server asks Git for the branch and commit instead and reuses the answer for 250 milliseconds. A Git file that cannot be read after a few quick retries is treated as unknown rather than as a change: the request proceeds and the next request reads it again.

Git's `index.lock`, `HEAD.lock` and the reftable `tables.list.lock`, along with an in-progress rebase, cherry-pick or revert, suspend requests and sync batches while Git works. Git releases `index.lock` before it rewrites `HEAD` during a checkout, so both locks must stay absent for 200 milliseconds before the server checks identity, and each sync batch is checked again just before it is sent. A lock or operation that stays unchanged for 10 seconds is treated as stale or waiting on the user, such as `git commit` waiting for an editor or a rebase paused on a conflict. The server logs one warning and continues syncing. One request waits for Git at most 15 seconds in total, even when Git takes one lock after another. While a batch waits, the server keeps the history that connected sync sockets still need, so a large pull, merge or reset does not force Studio to resync; only the 64 MiB history budget can trim it. A cursor returned by `/api/read` is kept for five minutes, which covers the initial sync confirmation dialog. Restart the server, or return to the original branch and commit, and reconnect Studio after a branch change. Separate Git worktrees and separate serve ports avoid changing the source beneath a connected place.

## Available operations

| Operation | Contract |
| --- | --- |
| `sessions`, `status`, `capabilities` | Connected session identity, current mode and explicit capability/reason fields. Sessions expire after 30 seconds without polling. |
| `tree` | Bounded hierarchy traversal, up to 2,000 instances and depth 10. Returns stable IDs for the current bridge session. |
| `properties` | Up to 64 requested properties with typed Rojo values or per-property errors. |
| `selection` | Current Studio selection, up to 2,000 instances. |
| `logs` | Up to 200 bounded messages observed by the bridge's Edit-context LogService listener since connection. This is not a complete play-server log archive. Each entry has a `sequence` number, so `--after` and `--follow` can read only new entries; see [Following logs](#following-logs). |
| `export` | Native `SerializationService` model bytes written unchanged to a new `.rbxm` file. DataModel/services cannot be exported. Limit 5 MiB and 10,000 descendants. |
| `import` | Validated `.rbxm` or `.rbxmx` model insertion in Edit mode. The server validates the decoded model itself before queueing it, so callers that skip the CLI get the same checks. Existing siblings are preserved. Limit 5 MiB and 10,000 instances. No services or DataModel. Script source requires `--allow-scripts`; imported Script/LocalScript instances remain disabled. |
| `test` | Public `StudioTestService.ExecuteRunModeAsync` with a temporary controlled server runner calling `EndTest` after 1-5 simulation seconds. Returns the native result and whether Studio returned to Edit. It runs the project's existing scripts; completion alone is not an assertion that all gameplay tests passed. |
| `spec` | Runs the place's TestEZ (or Jest-Lua) `*.spec` modules in Run mode through the same runner mechanism as `test`, with a fixed runner source and the plugin's `SpecRunner` module, and returns a bounded report. Arguments are data only: `roots` (up to 32 `game/...` paths), `framework` (`auto`, `testez` or `jest`), `module` (the framework's ModuleScript), `filter` and `timeoutSeconds` (1-300, default 60). `rojo test` is the command-line client; see [Running specs](testing.md). |
| `cancel` | Cancels a pending caller-assigned request ID. The original caller receives HTTP 410 with `cancelled: true`, which is distinct from the 504 deadline response. The ID can be reused immediately. A cancel for an ID that is not queued (still waiting for Git or its import check, already finished, or not sent yet) returns HTTP 404, and the next command with that ID within 60 seconds is answered with HTTP 410 instead of being sent to Studio. Import revalidates the request before insertion. Cancellation cannot reverse a mutation that already committed, or instantly interrupt an already-started engine simulation. |

The capability response explicitly marks arbitrary Luau execution, native whole-place save/publish, and general play-mode controls unavailable, with reasons. Unyielding Luau cannot be safely interrupted by a plugin. Whole-place snapshots must come from a place file saved through Studio, rather than a model serializer applied to services.

```text
rojo studio --token-file <token> --json tree --session <id> --instance game/ReplicatedStorage --depth 3 --limit 500
rojo studio --token-file <token> --json properties --session <id> --instance <instance-id> --property Name,Size
rojo studio --token-file <token> --json export --session <id> --instance <instance-id> --output NativeUI.rbxm
rojo studio --token-file <token> --json import --session <id> --parent <folder-id> --input NativeUI.rbxm
rojo studio --token-file <token> --json test --session <id> --seconds 1
rojo test --token-file <token> --session <id> --root game/ReplicatedStorage/Shared
rojo studio --token-file <token> --json logs --session <id> --follow
```

Instance arguments accept an ID from inspection or an exact `game/...` path. Each name in a path is separated by `/`; a `/` or `\` inside a name is escaped with a preceding `\` (`game/Workspace/a\/b` is the instance named `a/b`). Inspection results describe each instance with `path` (escaped, accepted as an argument), `pathSegments` (the unescaped names starting with `game`, for tools that handle names themselves) and `fullName` (Roblox's dotted `GetFullName()` form, for display only). Duplicate-named siblings make a path ambiguous, so use IDs for those instances. IDs stay valid until the instance is destroyed and expire when the bridge reconnects. Imported instances are changes to the current Studio session; exporting or saving through Studio is still necessary for persistence. Normal Rojo project rules continue to determine what survives future synchronization.

To prepare cancellation, assign a UUID with `--request-id <uuid>` to the original command, then run `cancel --session <id> --request <uuid>` with the same token and address. Commands have a 15-second response deadline once queued. Counting the wait for Git (up to 15 seconds), reading the body (10) and checking an import (15), the server answers a command request within 60 seconds, and `rojo studio` waits 65 seconds. A `spec` command's deadline is its `timeoutSeconds` plus 30 seconds for entering and leaving Run mode, at most 330 seconds; the server rejects other `timeoutSeconds` values with HTTP 400. Its `expiresAt` and the server's pending entry follow that deadline, the request is answered within that deadline plus 45 seconds, and `rojo test` waits 5 seconds longer. The plugin cannot poll while Studio is in Run mode, so during a `test` or `spec` run it sends a `validate` request for the command every 5 seconds, which keeps the session from expiring after 30 seconds. A `validate` keeps the session alive even after its request was cancelled or expired, when the server answers it with 410: Studio is still in Run mode and polls again once it ends, so cancelling a run (Ctrl-C on `rojo test`, `rojo studio cancel`, or an MCP cancellation or timeout) does not take the bridge down. The plugin stops sending them once the run has lasted 30 seconds past its expected length, so a Run mode that never ends does not keep a session that cannot answer listed. That 30 seconds is counted from when the runner is inserted, since the plugin cannot observe when Run mode actually starts; if Studio takes longer than the run's `timeoutSeconds` plus 30 seconds to enter Run mode, the runner can be removed before Run mode copies it, and the run then cannot report a result. If the session expired during Run mode anyway, the first poll afterwards gets 404, and the plugin registers the same session again, once, instead of stopping. A `spec` command starts Run mode only when at least its `timeoutSeconds` plus 10 seconds of its deadline remain; one that waited behind another run with less left fails with an error saying to run it again. Other commands for that session wait until Run mode ends and may reach their own 15-second deadline first. A cancel for a request ID that is not queued yet is remembered for 60 seconds, so a command still waiting for Git or its import check is answered with HTTP 410 instead of being sent to Studio. Bodies and responses are bounded at 8 MiB, and at most 32 commands may be pending. At most 16 sessions stay registered with a server; registering another evicts the session that polled least recently, whose pending commands fail and whose next poll receives HTTP 404. Import models are decoded in a separate `rojo` process, at most two at a time, with a 768 MiB memory cap and a 15-second limit that includes waiting for a slot. A model that crashes the decoder, runs out of memory or overflows the stack ends only that process, and the command fails with "Import model could not be decoded". `rojo studio import` checks its input the same way. The session must exist before the check starts. Before decoding, the checker also compares the instance, chunk, string and array counts a binary model declares with the bytes that follow, and rejects XML models that nest `<Item>` elements more than 512 levels deep, are not UTF-8 or declare a document type or entities, so most bad models fail with a specific reason. Queued commands for one session may hold at most 64 MiB; further commands receive HTTP 429 until earlier ones finish. A poll returns at most 6 MiB of commands (always at least one) and leaves the rest queued. A single command too large for one poll response under the plugin's 8 MiB limit is rejected with HTTP 413 instead of being queued. Commands are delivered at most once: if a poll response is lost, the command is not resent and its caller times out, so an import is never applied twice. Repeating a registration with the same session ID and description succeeds, so the plugin can retry after a lost response.

## Following logs

The plugin numbers every captured message with a `sequence` that starts at 1 for each bridge session and keeps increasing, also when the 200-entry buffer drops its oldest entries. `rojo studio logs --follow` prints entries as they arrive until you press Ctrl+C:

```text
rojo studio --token-file <token> logs --session <id> --follow
rojo studio --token-file <token> --json logs --session <id> --follow --after 0
```

Without `--after`, following starts with the newest `--limit` entries (100 by default), like `tail -f`. `--after N` starts with the first entry after sequence `N`, so `--after 0` prints every entry still in the buffer. The CLI asks for new entries every second. With `--json`, each entry is printed as one JSON object per line (`sequence`, `kind`, `message`, `timestamp` in Unix milliseconds). Without it, each line reads `[sequence] Kind: message`. When entries were dropped from the buffer before they could be read, for example during a burst of more than 200 messages, a notice with the number of lost entries goes to stderr, so stdout keeps only entries. After five failed requests in a row, such as when the session expires, `--follow` stops with the last error. Studio cannot answer while it is in Run mode, for example during `rojo test`, so following stops after five requests in a row time out; start it again once the run ends.

For incremental reads without polling, pass `--after` without `--follow`. The result is then an object instead of a list:

| Field | Meaning |
| --- | --- |
| `entries` | Up to `--limit` entries with a sequence greater than `after`, oldest first. |
| `latestSequence` | The sequence of the newest captured message. |
| `nextAfter` | The value to pass as `--after` on the next read. |
| `more` | `true` when more new entries are waiting than `--limit` allowed. Read again with `nextAfter` right away. |
| `dropped` | How many entries after `after` were dropped from the buffer, or cleared when the bridge stopped, before they could be read. |
| `restarted` | `true` when `after` was ahead of `latestSequence`. The entries then start from the oldest one still kept. |

`rojo studio logs` without `--after` or `--follow` still returns the plain list of the newest entries, so scripts written for it keep working. Plugins from before follow mode return that list and no `sequence` numbers; `--after` and `--follow` then fail and ask you to update the plugin. `capabilities` reports `logs.follow: true` for plugins that support it.

## Authentication boundary

The CLI token is made of two random UUIDv4 values (244 random bits, 64 hex characters) stored only in the caller-chosen file. Creation never overwrites an existing token or prints its contents. On Unix, `rojo serve` and `rojo studio` warn when the token file can be read by its group or other users. Requests require that token, a loopback peer, and no `Origin` header. The existing Host/Origin protections still run first.

The plugin receives a separate registration token through the initial local Rojo handshake. That token can register/poll/answer for plugin sessions but cannot list sessions or submit commands. Pairing information is included only for a loopback peer without an `Origin` header whose `Host` header is `localhost`, `127.0.0.1` or `[::1]`, with an optional port. A DNS rebinding page arrives under its own host name, so it cannot read the token even when `--address 0.0.0.0` disables host validation. The unauthenticated pairing response carries an opaque identity digest instead of local paths; the plugin echoes it back unchanged. Authenticated session listings still report the full identity.

The plugin token is not a secret from local software. Any process that can reach the loopback port can read it from `/api/rojo`, and on most systems that includes processes run by other OS users on the same machine. Such a process can register sessions that look like Studio to agents, answer their commands with invented results, or evict the real Studio's session. It cannot list sessions or issue commands without the CLI token. Pairing is not authenticated against the OS user, with one exception: on Linux the server looks up the owner of each loopback connection in `/proc/net/tcp` and `/proc/net/tcp6` and refuses pairing and bridge requests from connections owned by another user. Windows and macOS have no equivalent check. Enable the bridge only on single-user machines, or on machines where every local user is trusted. Compare `placeId`, `placeName` and `registeredAt` from `sessions` with the Studio window you expect before targeting a session. This boundary is not a defense against malicious local processes.

## Verification

On Studio `0.745.0.7451137`, an isolated disposable Edit fixture verified real CLI session discovery, status, bounded tree inspection, typed Text/UDim2 properties, a 3,967-byte native UI export, native re-import preserving the TextLabel, and a native one-second Run simulation returning to Edit in 2.67 seconds. The same import path loaded Wally and pesde package fixtures, and their consumer modules returned the expected Promise results; the native pesde relative string require also resolved.

Plugin TestEZ verification passed 111 tests with no failures and one existing skipped test. Backend regressions cover authentication, browser/remote rejection, token role separation, result ownership, request/result delivery, cancellation, body limits and Git checkout identity guards. No existing user place was modified during these disposable-fixture checks.

A real CLI cancellation during a five-second native Run simulation discarded the late result, then completed a queued status command successfully. The same bridge ID remained registered and normal Rojo sync stayed Connected. Authentication failures and malformed responses still disconnect the bridge; only a valid HTTP 410 response to late result delivery is treated as normal cancellation/expiry.

Changing the disposable server's Git identity after connection caused fresh `/api/rojo`, `/api/read/...` and `/api/write` requests to return HTTP 409. Responses to requests sent with `x-rojo-content-transfer: base64`, including errors and `/api/studio/` routes, use the same encoding and carry the same header, so the plugin can decode them. The one exception is the generic 404 for a request that fails Host/Origin validation, which stays unencoded so that it does not identify a Rojo server. The plugin treats any unencoded response that has headers as coming from a server without encoded streams, and sends plain requests to that origin from then on. The existing Studio sync and bridge disconnected and cleared their tracked requests. The helper server was then stopped.
