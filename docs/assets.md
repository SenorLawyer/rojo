# Asset sync

`rojo assets sync` uploads the images, sounds and models in a folder to Roblox through Open Cloud and writes a Luau module with their ids. Code refers to `Assets.Icons.Coin` instead of a hard-coded `rbxassetid://` string, and the ids live in version control next to the files they came from.

Only new or changed files are uploaded. A rerun with no changes makes no network requests and does not need an API key.

## Setup

Create `assets.toml` next to your project file:

```toml
# Folder with the files to upload, relative to this file.
source = "assets"
# Module to write, relative to this file.
output = "src/shared/Assets.luau"

# Optional. Put in front of every display name on Roblox.
name_prefix = "MyGame "
# Optional. Defaults to "Uploaded by rojo assets sync from <path>".
description = "MyGame asset"

# Optional. Only sync paths that match one of these globs.
include = ["**/*"]
# Optional. Skip paths that match one of these globs.
exclude = ["**/*.psd", "Drafts/**"]

# Who owns the uploaded assets: exactly one of user_id or group_id.
[creator]
user_id = 123456789
# group_id = 987654
```

Globs are matched against paths relative to `source` with `/` separators. `*` stays within one folder and `**` crosses folders, so `*.png` only matches files directly in `source`. Files and folders whose names start with `.` are always skipped.

Create an API key at [create.roblox.com/credentials](https://create.roblox.com/credentials) with the **Assets** API's `asset:read` and `asset:write` scopes, and put it in the `ROBLOX_API_KEY` environment variable. For a group creator, the key must belong to the group.

## Workflow

```
assets/
  Icons/
    Coin.png
    Gem.png
  Sounds/
    Jump.ogg
```

```sh
rojo assets status          # what is new, changed, renamed or missing; no network
rojo assets sync --dry-run  # what would be uploaded; writes nothing
rojo assets sync            # upload, then update the lockfile and the module
```

`sync` prints each upload as it goes:

```
  new       Icons/Coin.png (Image, 1.2 KB) to upload
  ...
[1/3] Uploading Icons/Coin.png (Image, 1.2 KB)... asset 1111111111
```

and writes `src/shared/Assets.luau`:

```lua
--!strict
-- Generated by rojo assets sync; do not edit.

return {
	Icons = {
		Coin = "rbxassetid://1111111111",
		Gem = "rbxassetid://2222222222",
	},
	Sounds = {
		Jump = "rbxassetid://3333333333",
	},
}
```

```lua
local Assets = require(ReplicatedStorage.Shared.Assets)
icon.Image = Assets.Icons.Coin
```

Commit `assets.toml`, `assets.lock.json` and the module. Teammates who pull get the same ids and only upload files they add or change themselves.

Options:

- `--config <path>`: use another config file. Its lockfile is named after it: `ui.toml` uses `ui.lock.json`.
- `--api-key-env <NAME>`: read the key from another environment variable. Defaults to `ROBLOX_API_KEY`.
- `--dry-run`: list what would be uploaded and write nothing.
- `--retry-rejected`: upload files again whose exact contents Roblox rejected in moderation before. See [Moderation and errors](#moderation-and-errors).

Only one `sync` can run for a config at a time. While it runs, `sync` holds `assets.lock.json.lock` next to the lockfile, which records its process id and start time, and removes it when it finishes or fails. A second `sync` for the same config refuses to start and names the file. A sync that is interrupted or killed, including with Ctrl+C, does not get to remove the file and leaves it behind; the next `sync` then refuses to start. Check that no sync is still running (the file names the process id), then delete `assets.lock.json.lock` and run `sync` again. Uploads that the interrupted sync recorded are kept. `status` and `--dry-run` write nothing and do not need it. Add `*.lock.json.lock` to `.gitignore`.

## The module

- Folders become nested tables and files become keys named after the file without its extension.
- Keys that are not valid Luau identifiers are quoted, as in `["Big Coin"]` or `["2x"]`.
- Keys are sorted, so the module only changes when an id or file changes. It is only rewritten when its contents change, so `rojo serve` does not see spurious edits.
- Two files that would get the same key, such as `Coin.png` and `Coin.jpg` in one folder, or `Icons.png` next to an `Icons` folder, stop the sync before anything is uploaded. The error names both paths.

## The lockfile

`assets.lock.json` maps each file's path to the BLAKE3 hash of its contents, its asset id, asset type, creator, moderation state and upload time.

- A file is uploaded when no entry has the same contents, asset type and creator. Renaming, moving or copying a file reuses its id without uploading.
- Changing the creator uploads every file again under the new creator. Each old id that a new upload replaces is recorded under `replaced`, keyed by the old id, with the new id, the path, asset type, both creators and the time. See [Moving to a group](#moving-to-a-group). If a file's old contents moved to another path that has not been uploaded yet when a sync stops, the old id is kept under `displaced` until that upload records it; a sync that finishes empties `displaced`.
- A file that is gone is dropped from the lockfile and the module, and reported. The asset is never deleted on Roblox, since the Assets API cannot delete assets and published places may still use it.
- The lockfile is rewritten after every successful upload, through a temporary file and a rename. If a sync is interrupted or an upload fails, what was uploaded so far is kept and the next sync continues from there. The module is only written once every upload has succeeded.
- As soon as Roblox accepts a file, the lockfile records the upload's operation under `pending`, keyed by the asset type, creator and hash of the contents that were sent, together with the path they were sent from. If checking on it then fails (a network outage, a key without `asset:read`, or processing taking longer than five minutes), the next sync checks on that operation again instead of sending the file a second time, and prints `resume` for it. The pending upload is found by contents, so it is resumed for whichever file has those contents now, even if the file was renamed and new contents were written under the old name. A pending upload whose contents no file has any more is dropped from the lockfile after the next successful sync with the same creator; any asset Roblox made for it stays unused. Pending uploads for another creator are kept until a sync with that creator.
- If a pending upload keeps failing, for example because Roblox no longer knows the operation, check the creator's assets on Roblox, then delete its entry under `pending` in the lockfile (the error names the entry, and its `path` names the file) to upload it again.
- A file can only be uploaded twice if the sync stops after sending it and before Roblox's reply is recorded, such as a dropped connection during the upload request. The error says when that may have happened.
- Contents that Roblox rejected in moderation are recorded under `rejected`, keyed by their hash, with the path, asset id, asset type, creator and time. See below.
- The lockfile has a `version`. A Rojo that finds a version it does not know refuses the lockfile instead of rewriting it, so an older Rojo never drops what a newer one recorded. A lockfile with `replaced` or `displaced` entries has version 2, which Rojo 8.0.0 refuses, since it would drop them; every other lockfile keeps version 1.

If two branches both add assets, keep both sides' entries when resolving the conflict and run `rojo assets status` to check.

## Moving to a group

Asset ids belong to their creator, so moving a game from your account to a group means uploading every asset again under the group and replacing every use of an old id. `sync` does the uploads and remembers which old id became which new one; `rojo assets remap` finds and rewrites the old ids.

1. Change the creator in `assets.toml`:

   ```toml
   [creator]
   group_id = 987654
   ```

2. Create an API key that belongs to the group, with the `asset:read` and `asset:write` scopes, and put it in `ROBLOX_API_KEY`.
3. Run `rojo assets sync`. It uploads every file again under the group and rewrites the module, so code that uses the module needs no change. Each old id is recorded under `replaced` in the lockfile, found by path and by contents, so a file moved during the switch keeps its mapping. An interrupted sync keeps what it recorded, and the next sync continues. `rojo assets status` says how many ids were replaced.
4. Run `rojo assets remap` to list the files that still use an old id, then `rojo assets remap --write` to rewrite them:

   ```
     src/shared/Shop.luau:12  1111111111 -> 4444444444
     src/client/Hud.model.json:30  2222222222 -> 5555555555
   Scanned 214 file(s) for 312 replaced id(s): 2 reference(s) in 2 file(s).
   Nothing was written; run again with --write to rewrite them.
   ```

5. Place content outside your files, such as a `Decal.Texture` or `Sound.SoundId` set in Studio, still has the old ids. Write the mapping with `rojo assets remap --map-out asset-ids.json` and run the script below in Studio, for example through the command bar or a Studio MCP tool, then save the place.

Commit the lockfile with its `replaced` section, so teammates can run `remap` on their branches too. If you switch creators again, the earlier records point to the newest ids. Delete the `replaced` section once nothing uses the old ids. If records under `replaced` form a cycle, such as `123 -> 456` and `456 -> 123` after a bad merge, or lead to the id `0`, `remap` stops with an error naming the ids before reading or writing any file, including the `--map-out` file; fix or remove those records first.

`remap` reads `rbxassetid://<id>`, Roblox asset URLs, and `rbxthumb://` URIs of `type=Asset`. A URL must be `http` or `https` with the host `roblox.com`, `www.roblox.com` or `assetdelivery.roblox.com` exactly and the path `/asset` or `/v1/asset` (with or without a trailing `/`), with the id in an `id=` query parameter, such as `https://www.roblox.com/asset/?id=<id>`; other hosts, such as `notroblox.com` or `roblox.com.example.com`, are left alone. Thumbnails of other types, such as `type=Avatar` or `type=GameIcon`, take user or universe ids and are left alone too. A number only matches as a whole, so the id `123456789` is never found inside `1234567890`. Options:

- `[paths]...`: files or folders to read. Defaults to the folder holding `assets.toml`. Folders are walked for `.lua`, `.luau`, `.json`, `.toml`, `.csv`, `.tsv`, `.txt`, `.md`, `.yaml`, `.yml`, `.xml`, `.rbxmx`, `.rbxlx` and `.html` files, skipping hidden folders such as `.git`, `node_modules`, `Packages`, `ServerPackages`, `DevPackages` and `target`. Files given by name are read whatever their extension, and folders given by name are walked even if they would be skipped. Every `*.lock.json`, the config, the generated module and the `--map-out` file are always skipped.
- `--write`: rewrite the references. Files are rewritten through a temporary file and a rename, and everything except the ids stays byte for byte, including line endings. Without it, nothing is written.
- `--bare`: also match numbers on their own equal to an old id, as in `local COIN = 1111111111`, but not parts of words, decimals or versions. Any number can happen to equal an id, so check the list before adding `--write`. Without it, `remap` says how many such numbers it left alone.
- `--map-out <file>`: write every old id and its newest id as JSON, such as `{ "1111111111": 4444444444 }`. Written with or without `--write`.
- `--json`: print a report with each reference's `path`, `line`, `kind` (`assetId`, `url` or `bare`), `oldId` and `newId`, and the counts.
- `--config <path>`: use another config file.

`remap` exits with 0 whether or not it finds references, and with an error only when it cannot read the config, the lockfile or a file, or cannot write one.

Only assets uploaded with `rojo assets sync` are tracked. Assets uploaded in Studio, through the Toolbox or by another tool are not in the lockfile, so they cannot be moved or remapped this way: add their files to the asset folder and sync them, then replace their ids by hand. Packages, the Toolbox and other places are not read either.

This script rewrites asset properties in the open place. Paste the `--map-out` file between the brackets:

```lua
local ChangeHistoryService = game:GetService("ChangeHistoryService")
local HttpService = game:GetService("HttpService")

local map = HttpService:JSONDecode([[
{ "1111111111": 4444444444 }
]])

-- Properties that hold asset ids. Add any others the place uses.
local PROPERTIES = {
	"Texture", "Image", "HoverImage", "PressedImage", "SoundId", "MeshId", "TextureID",
	"TextureId", "AnimationId", "ShirtTemplate", "PantsTemplate", "Graphic", "Video",
	"SkyboxBk", "SkyboxDn", "SkyboxFt", "SkyboxLf", "SkyboxRt", "SkyboxUp",
	"SunTextureId", "MoonTextureId", "TopImage", "MidImage", "BottomImage",
	"BaseTextureId", "OverlayTextureId",
	"TextureContent", "ImageContent", "AudioContent", "MeshContent", "VideoContent",
}

local function swap(prefix: string, id: string): string
	local new = map[id]
	-- %.0f, since tostring could print a large id in exponent form.
	return prefix .. (if new then string.format("%.0f", new) else id)
end

local function remapUri(uri: string): string
	local result = uri:gsub("([rR][bB][xX][aA][sS][sS][eE][tT][iI][dD]://)(%d+)", swap)
	result = result:gsub("([?&][iI][dD]=)(%d+)", swap)
	return result
end

-- The new value for a property, or nil to leave it alone.
local function remapValue(value: any): any
	if typeof(value) == "string" then
		local new = remapUri(value)
		return if new ~= value then new else nil
	elseif typeof(value) == "Content" then
		if value.SourceType == Enum.ContentSourceType.Uri and value.Uri then
			local new = remapUri(value.Uri)
			return if new ~= value.Uri then Content.fromUri(new) else nil
		end
	elseif typeof(value) == "number" then
		-- CharacterMesh ids are numbers.
		return map[string.format("%.0f", value)]
	end
	return nil
end

local recording = ChangeHistoryService:TryBeginRecording("Remap asset ids")
local changed = 0
for _, instance in game:GetDescendants() do
	for _, property in PROPERTIES do
		-- Most classes lack most of these properties, and some cannot be set
		-- from scripts, so both the read and the write may fail.
		local ok, value = pcall(function()
			return (instance :: any)[property]
		end)
		local new = if ok then remapValue(value) else nil
		if new ~= nil and pcall(function()
			(instance :: any)[property] = new
		end) then
			changed += 1
		end
	end
end
if recording then
	ChangeHistoryService:FinishRecording(recording, Enum.FinishRecordingOperation.Commit)
end
print(`Remapped {changed} asset propert{if changed == 1 then "y" else "ies"}`)
```

Setting a legacy property such as `Decal.Texture` also updates its `Content` property, as described in [Asset properties and Content](content-properties.md). Properties that scripts cannot set, such as `SurfaceAppearance.ColorMap`, are skipped; change those by hand.

## Supported files

| Extension | Uploaded as | Notes |
| --- | --- | --- |
| `.png`, `.jpg`, `.jpeg`, `.bmp`, `.tga` | Image | Must be smaller than 8000x8000 pixels. |
| `.mp3`, `.ogg`, `.flac`, `.wav` | Audio | Roblox limits audio to 7 minutes, and to 10 uploads a month (100 when ID-verified). |
| `.fbx`, `.gltf`, `.glb` | Model | Imported as a Model with MeshParts and uploaded as a package. A `.gltf` must embed its buffers and textures. |

Every file must be at most 20 MB (20,971,520 bytes). Rojo checks sizes, image dimensions and file signatures before uploading anything; a file that fails these checks stops the sync. Other extensions, including `.obj` (which Open Cloud does not accept), are skipped with a warning; add them to `exclude` to silence it.

Images are uploaded as `Image`, not `Decal`. A Decal's id does not load in `ImageLabel.Image` or `Texture.Texture`; an Image's id does.

Models are uploaded as `Model` assets, and the module holds the Model's id as `rbxassetid://<id>` like every other entry. That id is not a mesh id: setting it as a `MeshPart.MeshId` does not work. Load the model with `InsertService:LoadAsset(id)` on the server (strip the `rbxassetid://` prefix and convert it with `tonumber`), which returns a `Model` holding the imported MeshParts, or insert it in Studio from the Toolbox under your creations. Reuse the MeshParts from there rather than their individual mesh ids.

Audio duration and upload quotas are only checked by Roblox, so such failures show up as an upload error.

## Moderation and errors

- An asset that Roblox rejects in moderation stops the sync with an error naming the file. Its id is not used, and the rejection is recorded under `rejected` in the lockfile.
- A later sync does not upload those exact contents again, at any path, since each upload makes another rejected asset on the creator's account. Instead it stops before uploading anything, naming the file and the rejected asset. `rojo assets status` and `sync --dry-run` list such files as `rejected`. Replace the file (any change to its contents uploads it as usual) or add it to `exclude`. If you think the rejection was a mistake and want to try the same file again, pass `--retry-rejected`; if Roblox accepts it this time, the record is removed.
- Rejection records stay in the lockfile after the file changes, so restoring the rejected contents does not upload them again. Delete an entry under `rejected` by hand to forget it.
- An asset still under review (moderation state `Reviewing`) is recorded with a warning. Its id may not load until it is approved. `rojo assets status` lists assets that were not approved when they were uploaded.
- The recorded moderation state is never refreshed. It is what Roblox reported when the upload finished; a later approval or rejection does not change the lockfile, and `rojo assets status` keeps listing the asset as `Reviewing`. Check the asset on the Creator Dashboard for its current state. If Roblox later rejects it, replace the file so the next sync uploads it again.
- Rate-limited requests (HTTP 429) are retried with backoff. A failed upload request is not retried, since Roblox may already have created the asset; the error says so when that is possible. Failures while checking on an accepted upload are resumed by the next sync, as described under the lockfile above.
